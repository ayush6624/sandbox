The 128-way failure, fully attributed

All 48 failed creates landed on worker 10.160.0.7 and reported the same error:

configure VM cgroup io.max: .../io.max: no such device

CheckFailing workerHealthy worker
Data disk/dev/sdb XFS, unmounted/dev/sdb XFS, mounted
/mnt/sandbox-databoot partition /dev/sda1 · 8:1data disk /dev/sdb · 8:16
fstab entries for mountpoint5 stale UUIDs1 current UUID
Startup resultxfs_growfs failed, ignoredmount and grow succeeded
AdmissionNomad started; 48 slots advertisedNomad started after valid mount

This is a startup/admission bug, not the original create-latency bug. The worker script accumulated stale UUID lines, failed to establish the mount, suppressed the only explicit failure with || true, stamped data_disk_ready, and admitted the worker.

Post-campaign fix implemented: startup now replaces all fstab rows for this mountpoint, mounts the named disk explicitly, validates mountpoint + filesystem + backing major:minor + read-write options before and after mandatory XFS growth, and keeps Nomad disabled and stopped until every admission check passes. Template sandbox-workers-tpl-20260729-093155 is deployed and stable at two running plus six suspended workers; both active workers passed direct disk validation and a create/delete smoke left zero sandboxes. Release 9b6a9fc predates the fix, so the 128-way rebenchmark still remains.

Security and cleanup

No benchmark bypassed production security. Every created VM used jailer exec and chroot, dedicated UID/GID, a PID namespace, a cgroup leaf, seccomp, independent tap/IP/rootfs, guest network re-identification, agent readiness checks, and fresh Ed25519 host-key rotation.

  • All source and batch resources were deleted.
  • Fleet cleanup verified 32/32, 64/64, 80/80, 64/64, and 64/64.
  • The density worker returned from 41 Firecracker processes to its nine-process baseline before the anchor was deleted.
  • Final gateway-wide sandbox count: 0.
