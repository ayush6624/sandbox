second. Every sandbox executed `printf benchmark-ready`, remained alive for two
seconds, and was deleted. Final metadata discovery found no run-owned sandboxes,
and GET returned 404 for all 60 observed IDs.

## Interpretation

This short run demonstrates replenishment of the default warm pool at five
arrivals per second for this workload. It does not establish saturation,
sustained capacity, tail latency, or behavior when the pool is exhausted.
Arrivals are independent of earlier job completion. The scheduler test holds
early requests open and rejects another while verifying that later arrivals
still dispatch.

All times include the workstation's SSH tunnel to the development gateway.
Metric samples are roughly 500 ms apart plus scrape time, so a sampled zero
queue depth cannot rule out short waits between samples. Per-request server
queue time is unavailable on this deployed build. No pool, autoscaler, image,
or service configuration changed.

The next proposed stage is 160 creates at 20 arrivals per second with the same
two-second hold. Automatic approval review rejected that increase for shared
fleet disruption and cost risk without explicit approval. It has not run.

## Reproduce

From `sdk/typescript`, set `SANDBOX_API_URL` and `SANDBOX_API_KEY`, then provide
observed release, guest-image hash, runner location, and cache conditions through
the standard `BENCH_RELEASE`, `BENCH_GUEST_IMAGE_SHA256`, `BENCH_RUNNER_REGION`,
and `BENCH_CACHE_STATE` variables.

```sh
BENCH_COUNT=60 BENCH_RATE=5 BENCH_HOLD_MS=2000 \
  BENCH_OUTPUT=benchmarks/results/open-loop.json npm run bench:open-loop
npm run bench:validate -- benchmarks/results/open-loop.json
```

Use a quiet development fleet. The runner attaches a unique metadata label and
ten-minute TTL to every sandbox. It disables create retries, records failures,
discovers run-owned resources during cleanup, and checks deletion explicitly.
The report's `passed` field means requests, commands, metric scrapes, and cleanup
succeeded; it does not assert a latency SLO.

## Queue-duration telemetry awaiting deployment

Local gateway code now exposes `sandbox_create_queue_wait_seconds` as a
histogram with `outcome="reserved"`, `"timeout"`, or `"canceled"`. Buckets are
1, 10, 100, and 500 ms, then 1, 5, and 30 seconds, plus infinity.

Each observation measures one admitted wait for capacity. A request that retries
placement can contribute several observations. Requests rejected before queue
admission contribute none; the existing rejection counter covers them.
`reserved` means capacity was obtained, even if the subsequent worker create
fails. `canceled` includes a client context deadline. This histogram provides
aggregate queue timing and outcomes; it does not expose a per-request trace.

Tests exercise actual waits with virtual time, check all three outcomes through
the metrics HTTP handler, and verify that queue accounting returns to zero.
The deployed fleet still lacks this histogram until rollout approval and
verification are complete.
