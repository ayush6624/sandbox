**My recommendation is to compete on reliable, fast continuation of real agent workloads.** We already have memory snapshots, warm template placement, differential disk transfer, and peer transfer. The largest opportunities are completing remote restore paths, making accepted operations survive failures, and measuring useful work with a reproducible benchmark.

ASCII's documentation describes a broader ready-to-use workspace product. Its strongest ideas for us are lazy filesystem restore, explicit lifecycle contracts, versioned environments, and integration guides. Public documentation establishes their advertised behavior, not their internal implementation or independently measured performance.

ASCII leaves several openings we can test and demonstrate:

- Their stop/resume cannot preserve a live interpreter, an in-memory search frontier, or a running process at its execution point. Our strongest demonstration would branch an initialized agent workload, verify independent children, and measure time to their first useful result. Existing external TCP connections and duplicated external side effects require separate tests; memory continuity does not guarantee either is safe. [ASCII long-running tasks](https://docs.ascii.dev/box/long-running-tasks).
- Their FAQ explicitly says there is no activity-based idle timer. Platforms must implement their own countdown, while create, fork, and resume all consume starts. Our activity-driven hibernation is worth demonstrating through a complete idle → wake → useful work → billing cycle. [ASCII FAQ](https://docs.ascii.dev/box/faq), [our hibernation](../internal/server/hibernate.go).
- High concurrency is not high provisioning throughput. The documented $20 plan allows 100 concurrent boxes but only 10 starts/minute, 50/hour, and 150/day. The $500 plan allows 1,000 concurrent boxes but 55/minute, 275/hour, and 825/day. Negotiated limits can be higher. Burst comparisons must disclose account limits. [ASCII billing](https://docs.ascii.dev/box/billing).
- Their Harbor adapter does not execute Dockerfile build instructions. It also declares network policies, Compose, and accelerator support unavailable through that adapter. Docker itself is available inside Box. A compatible evaluation adapter with reproducible image preparation and enforced network policy would be useful differentiation if we implement and verify it. [ASCII Harbor adapter](https://docs.ascii.dev/box/integrations/harbor).

Their pricing deserves a real cost comparison: the documented default is $0.036/hour for 4 shared vCPUs and 8 GB RAM. Machine specifications explicitly say shared CPU, despite stronger wording on their marketing page. Compare sustained useful throughput and included services, not vCPU counts alone. The billing page includes snapshots and up to 2 TB monthly egress per box. Our existing billing tests use illustrative rates and do not establish infrastructure cost or price superiority. [ASCII machine specifications](https://docs.ascii.dev/box/machines), [billing](https://docs.ascii.dev/box/billing), [our pricing tests](../tests/usage-pricing-bench.ts).

I would prioritize these architecture changes:

1. **Make accepted operations recoverable across gateway restarts.** `internal/httpapi/httpapi.go:113` explicitly defines process-local idempotency. Its key scope at line 157 is method, path, and key. `internal/apiv1/handler.go:641` stores a batch in memory, returns 202, and launches a goroutine. This is an HA and restart limitation, not proof of a current production incident. Persist the request identity, operation, and resumable work in one durable transition. Assign stable item identities that workers reconcile after uncertain responses. Add principal scoping when introducing tenants. Simply persisting the two maps separately does not close the crash window. Acceptance: kill the gateway after a worker accepts creation but before the response reaches the client, retry through another gateway, and observe the same operation and at most one sandbox per item. ASCII documents account-scoped, 24-hour replay semantics for create and fork. [Our idempotency store](../internal/httpapi/httpapi.go), [batch acceptance](../internal/apiv1/handler.go), [ASCII API contract](https://docs.ascii.dev/box/api/v1).

2. **Make snapshot durability recoverable without blocking every local snapshot.** Local snapshots already expose `local` versus `durable`; GCS metadata is already committed last. However, `internal/server/snapshot_gcs.go:103` starts a single uploader, and failures leave the snapshot local. Add persistent upload intent, retry/reconciliation after restart, and a durable-completion wait with an observable error. Preserve the low-latency local path. Acceptance: interrupt upload, restart the worker with its disk intact, recover the object store, wait for durable completion, then restore on another worker. Loss of the only worker disk before upload completes remains a different failure mode and must be disclosed. [Snapshot upload](../internal/server/snapshot_gcs.go), [public durability state](../internal/apiv1/handler.go).

3. **Carry lazy memory loading through cross-host adoption.** `internal/server/hib_adopt.go:69` fetches nonzero memory chunks sequentially; reconstruction completes before clone wake. Reuse the existing chunk loader and working-set prewarm in a clone-capable lazy restore path. Disk reconstruction remains a separate cost. Acceptance: vary total state size independently from the accessed working set, force a cold destination host, and measure both first useful command and full workload completion. Test unavailable chunks and peer/source failure after initial readiness. This is a focused extension of existing infrastructure, not a new snapshot engine. [Adoption](../internal/server/hib_adopt.go), [existing lazy source](../internal/vm/uffd_source.go).

4. **Finish the per-VM network namespace integration.** `internal/provisioner/netns.go` already implements the intended fixed guest IP design, but the runtime clone path still performs guest identity changes and waits for announcements. Integrating namespaces can remove that guest work from readiness. Historical measurements in the source motivate the design, but they are not a verified speedup for an integrated release. Acceptance: simultaneous clones with identical guest IPs, inbound and outbound connectivity, wake/adopt, clock correction, and complete namespace cleanup after failures. Test under load before increasing warm-pool sizes to hide the same cost. [Namespace design](../internal/provisioner/netns.go), [current clone path](../internal/server/snapshot.go), [launcher](../internal/vm/launcher.go).

5. **Define ownership and retention guarantees before expanding persistent workloads.** Existing GCS compare-and-swap fencing arbitrates claims when reachable. The code deliberately favors local availability during some GCS failures, leaving an ownership ambiguity under partitions. Decide the partition policy explicitly: stronger compare-and-swap alone cannot guarantee both availability and a single live owner. Separately, shared memory chunks currently remain after deletion, and golden bases are retained indefinitely. Add reachability-based garbage collection before claiming predictable long-term storage cost. Acceptance: partition the old owner while another adopts, verify the chosen ownership behavior, then exercise create/fork/delete and account for all retained bytes. [Fencing](../internal/server/hib_fence.go), [invalidation tradeoff](../internal/server/hib_durable.go), [chunk retention](../internal/server/uffd_chunks.go).

Per-sandbox egress policy and tenant configuration belong in the next platform layer. The inspected provisioner has broad guest forwarding and inter-guest allow/deny, but no per-sandbox destination policy. That is an API and policy gap, not a demonstrated metadata-service vulnerability; deployed network controls were not inspected. Memory snapshots can also preserve credentials in RAM, so changing an environment file does not revoke previously loaded secrets. Use scoped, revocable credentials and test clone inheritance before offering user-owned workspaces. [Provisioner](../internal/provisioner/provisioner.go).

The next comparison should use one guest workload with provider-specific lifecycle adapters:

| Experiment | Main question | Measurements and checks |
| --- | --- | --- |
| Warm create, empty pool, scale from zero | How much latency depends on reserved capacity? | API acceptance, first command, first app response, pool occupancy, new-host readiness, failures. |
| Prepared workspace restore | When can an agent actually use the workspace? | Dependency access, SQLite query, build/test completion, file hashes, read stalls, downloaded bytes. |
| Live-state branch | What work must be repeated after a fork? | Initialized interpreter or in-memory state, independent child mutations, first useful result. Report unsupported process continuation explicitly for ASCII and measure its restart alternative. |
| Cold cross-host snapshot | Does peer transfer avoid object-store delay? | Local owner, cold target with peer, upload pending, peer unavailable with durable fallback, and both unavailable. Verify path counters and state correctness. |
| Bursty and sustained arrivals | Can the fleet absorb demand beyond warm capacity? | Offered versus completed starts, first-attempt success, eventual success, queue delay, p50/p95/p99 with sample counts and uncertainty. |
| Failure and recovery | Do accepted operations finish or remain inspectable? | Lost responses, gateway restart, worker death, failed upload, replay, orphan resources, duplicate billing, ownership partition. |
| Cost and density | What does a successful workload cost at a stated latency target? | Total worker cost including idle pools, storage, egress, retries, failed work, cleanup, and retained snapshots. |

Run the common workload at comparable CPU/RAM and with pinned dependencies. Record actual hardware, region, runner RTT, cache state, account quotas, guest image, and all provider settings. Explicit CPU/RAM overrides currently force our cold-boot path, so resource matching must not silently change the lifecycle being compared. Use a matching prepared template and disclose how it was prepared. [Our create path](../internal/server/server.go).

For load tests, arrivals must continue on a fixed schedule when prior requests slow down; a fixed number of workers issuing the next request only after completion hides overload. Use thousands of observations across repeated runs for tail claims, with errors and timeouts retained. Run N=1,4,8,16,32 branch experiments only within disclosed provider limits. Larger saturation runs need separately disclosed quotas. Include cloud-local and user-region clients as separate result sets.

I would implement the work in this order: correct benchmark timers and provenance, run the existing peer canary through the public API, then make operations and snapshot uploads recoverable. Use the corrected workloads to choose between lazy adoption and network namespace integration for the next performance change. Add lifecycle events to persisted transitions, and build the Python/evaluation adapter around proven semantics.
